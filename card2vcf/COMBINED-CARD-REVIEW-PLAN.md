The requirements are [First extraction of combined cards](SPEC.md#first-extraction-of-combined-cards) and [Reviewing job and address variants](SPEC.md#reviewing-job-and-address-variants). Use the [approved stacked demo](../stacked-link-with-demo.html) for the visual layout and interactions. See the [implementation record](../docs/IMPLEMENTATION.md#status) for delivery status and verification.

## 1. Track reads by source card

The extraction handler currently queues one request per image. It fills the form only when the person still has revision zero, empty field arrays, empty notes and an empty explicit display name. Combine increments the revision even for two blank drafts. Removing only the revision check would still send the second card’s result to suggestions once the first card fills the form. [Queue and result handling](public/app.mjs) · [Combine and extraction](public/domain.mjs)

- Store each card’s successful-read state and normalized observations in the person state captured by `History`. Use the existing card ID. Keep the queue’s transient progress and failure indicators separate. A validated, completed read can contain zero values or only warnings. A failed, cancelled or discarded response must leave the previous successful-read state intact.
- At dispatch, capture the card, its owner and the editable state needed for comparison. On return, verify that the request is still current and the card still belongs to that person. Commit the observation, accepted values, source attribution and pending suggestions in one history change. Undo and Redo must restore them together.
- Combine the per-card records when merging people. Detach must partition them and their pending suggestions by source card and remap surviving row references. Today Detach clears the original person’s suggestions. Cover both Combine orders, including combining two cards that have already been read.

## 2. Reconcile results field by field

- Add a domain operation that decides what to apply, what requires review, and what is already known. Reuse `fieldIdentity`, `applyExtraction` and the existing metadata compatibility checks for accepted content. Compare whole jobs and addresses. On a first read, an exact compatible match from a different card must still acquire that card as a source. Preserve distinct bilingual entries for explicit linking. [Field identities](public/fields.mjs) · [Merge and provenance](public/domain.mjs) · [Metadata compatibility](public/contact-metadata.mjs)
- On a repeat read, compare against that card’s observations as well as the current edited contact. An identical observation must not recreate a deleted row, reverse a correction, or repeatedly queue an accepted, dismissed or still-pending suggestion. Treat new values and conflicting changes as field-level proposals. A value missing from a later response is insufficient evidence to delete existing data. Check generated-name suppression and note blocks, and preserve manually entered nicknames.
- Protect manual additions, edits and deletions before and during extraction. Track the affected row or field and its former identity when a user edits or removes it. If the same result also supplies an unrelated safe value, apply that value immediately. Different printed entries in a repeatable field are not inherently a conflict. Test an active input before blur: the current editor sets a flag on input and commits on change, so a background render must preserve both the typed value and focus. [Form and render lifecycle](public/app.mjs)
- **Proposed warning format.** The current response provides `warnings: string[]`. Keep that format and add an optional `fieldWarnings` list to the prompt and validator, with a field key, optional row index and message. Validate the reference against the returned data and preserve its association through normalization. Where a warning cannot be localized, show it against the source card without guessing a field. Hold affected values for review, including the whole card if subject attribution is unresolved. Render actionable proposals beside the affected field, using section-level placement for absent or deleted rows. [Prompt](src/extraction-prompt.mjs) · [Response validation](src/schema.mjs)
- Keep pending extraction proposals connected to the existing review/export checks. Applying values or changing grouping invalidates review. A repeat read with no changes or new warnings should leave approval intact. Exclude read bookkeeping and picker state from the exported-content signature while retaining the existing warning for unresolved changes. [Review and export](public/app.mjs) · [Signature](public/domain.mjs)

## 3. Derive eligible pairs from provenance

- After each successful read, and after Combine, recompute candidates for the affected person. For a person with two combined cards, inspect jobs and addresses independently. Require one meaningful, distinct, unlinked row from each source for that field type. A shared deduplicated row, manual-only row, or multiple possible matches cannot establish the pair. Re-evaluate after edits, link/unlink, Detach and history navigation. Use card completion and source membership rather than a batch-complete event or display order.
- Identify decisions by field type and the two source-backed entries. Record **Keep separate** for that pair in history. Preserve the effect of an explicit unlink through deduplication and ID remapping. Neither decision disables later manual linking. Keep optional pair prompts separate from blocking extraction suggestions.
- Resolve actions against current row IDs. Reuse `groups`, `link`, `unlink`, `setStatus` and `primary` for group-wide changes, primary ordering and status validation. If a row disappears, close or refresh the picker before applying an action. [Group operations](public/contact-metadata.mjs)

## 4. Implement the approved review UI

Replace the Jobs and Addresses checkbox/link controls in the live editor with the demo’s stacked rendering. Bind the controls to the domain operations above. Retain editable fields, Add, Remove and Make primary in the live app. The demo’s fictional rows, fixed candidate IDs and disabled surrounding controls belong to the prototype. [Live editor](public/app.mjs) · [Live styles](public/styles.css) · [UI reference](../stacked-link-with-demo.html)

- Build one inline picker for the active entry. Candidate status dropdowns and link actions need independent click and keyboard targets. After a status edit, refresh eligibility and the visible group status while keeping the picker open and focus on the edited control. Preserve the selected person and active field when a later result arrives for someone else.
- Render a suggested pair beneath its second displayed entry. Drive the blue prompt, mismatch notice, immediate decisions and linked header from the spec and demo. Apply the equivalent address prompt specified in the text. The demo illustrates the job shortcut and manual address linking. Preserve the existing wire contract when exporting confirmed groups. ## 5. Verify through the normal workflow

Use fictional cards, a controllable fake model and a separate app/browser session. Run the following checks before recording implementation as complete.

| Check | Expected evidence |
| --- | --- |
| Combine two unread cards, then extract. Repeat in reverse operation order. | The person has the same accepted values and source ownership in both cases. The first card fills the form before the second finishes. A repeated phone appears once and survives Detach on both sides. |
| Delay a response, edit one field, delete another, and leave an input focused. Exercise scoped and unscoped warnings. | Safe values fill immediately. Edited, deleted and uncertain values follow their review paths. Typing survives the render. A subsequent identical read produces no duplicate proposal. |
| Fail or cancel the second read, retry, then undo and redo. | A successful first card stays applied. The second remains eligible for its first read until success. History restores data, suggestions, read state and review status. |
| Hold another person’s response open after the two-card person finishes. | Eligible job/address prompts are already available on the completed person. The batch continues, the active person stays selected, and ambiguous pairs remain available for manual linking. |
| Link, keep separate, unlink, change candidate status, and switch people. | Decisions persist per pair. Manual linking still works after dismissal. A mismatched job has an editable dropdown, a disabled link target and stable hover color. Editing it can enable the link in place. Address decisions remain independent. |
| Compare the live form with the approved demo at desktop and narrow widths. Export and parse the resulting contact. | Verify **Primary**, status placement, stacked versions, count and **Unlink** under **Link with…**, warning placement, focus/Cancel and no horizontal overflow. Verify primary order, explicit links, status and original photos in both export modes. |

Update the [deduplication browser tests](tests/browser/dedup.test.mjs) that currently expect whole-card suggestions and the [integration browser tests](tests/browser/integration.test.mjs) that exercise the old selection controls. Retain the [domain](tests/dedup.test.mjs), [metadata](tests/contact-metadata.test.mjs) and [workflow](tests/browser/workflow.test.mjs) coverage. Run `npm.cmd test`, `npm.cmd run test:browser` and `npm.cmd run test:contract` from `card2vcf`. Record actual results in the [implementation record](../docs/IMPLEMENTATION.md) when the changes land.
